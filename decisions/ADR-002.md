# ADR-002: Reject a message broker for letter email delivery; use a database outbox

- **Status:** Accepted
- **Date:** 23 October 2026
- **Linked to:** Design problem P4 (secondary effects), FR-12, FR-15, UC-02 step 6, docs/pattern-decisions.md

## Context
After a letter is issued, the system must email it to the student and log the delivery (FR-12, FR-15). The email server can be slow or down, and this must not stop the letter being issued. Our architecture is one deployable web application with one relational database.

## Decision
We will NOT add a message broker (such as RabbitMQ or Kafka). Instead, LetterIssuanceService saves an "email to send" row through the EmailOutbox interface in the same database transaction as the letter. EmailRetryWorker reads pending rows, sends them through NotificationSender, and marks each as sent or failed.

## Alternatives considered
1. **Message broker.** A realistic option, and it scales well. Rejected because it adds a second server to install, run and monitor, a new failure point, and a hidden dependency for a system with a small volume of letters.
2. **Send the email directly inside verifyAndIssue.** Simplest. Rejected because an email failure would fail or delay letter issuing, and failed emails would be lost.

## Consequences
- **Accepted:** emails go out with a small delay (the worker polls), and we need one extra table and one background worker.
- **Avoided:** extra infrastructure, extra deployment steps and accidental complexity.
- **Revisit if:** email volume grows so large that one worker cannot keep up.

## Test that confirms the decision
Stop the email server, issue a letter, and check that the letter is created and the outbox row stays "pending". Start the server again, and the worker should send the email and mark the row "sent".
