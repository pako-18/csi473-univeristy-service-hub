## Decision 1: `LetterRequest` is a domain class, not a status attribute on `Student`

**Context**
FR-10 allows staff to approve *or reject* a completion assessment, and FR-11
produces a letter only on approval. A rejected request therefore produces no
letter but must still be recorded. UC-08 requires each request to remain visible in the student's
request history, and a student may request again after their record is
corrected under UC-11, so more than one request can exist for the same
student over time, each with its own reference number, purpose and status.

**Choice**
`LetterRequest` is modelled as its own class with the association
`Student "1" -- "0..*" LetterRequest`. Reference number, request date, purpose
and status are attributes of `LetterRequest`, not of `Student`.

**Alternative considered**
Holding `letterStatus`, `requestedOn` and `letterPurpose` as attributes
directly on `Student`. This removes one class and one association from the
model.

**Consequence accepted**
The model carries an extra class, and any query for a student's current request
must navigate an association rather than read a field. We accept this because
the attribute version holds only one request at a time: a second request would
overwrite the first, leaving a rejection under FR-10 with no durable record of
which request was rejected or why.

**Traces to:** FR-10, FR-11, FR-12 - UC-02, UC-08

## Decision 2: `CompletionCheck` attaches to `Enrolment`, not to `Student`

**Context**
Eligibility is assessed against the requirements of a programme, not against a
student in the abstract: FR-04 compares earned credits to *their programme's*
requirement, FR-05 checks that programme's compulsory modules, and FR-06 its
elective thresholds. A student may hold more than one enrolment over time - a
change of programme, or a second qualification - and each carries a different
set of `CompletionRequirement` records.

**Choice**
`CompletionCheck` associates to `Enrolment` (`Enrolment "1" -- "0..*"
CompletionCheck`), and `Enrolment` links `Student` to `Programme`. A check
therefore always resolves against exactly one programme's requirements.

**Alternative considered**
Attaching `CompletionCheck` directly to `Student` and reading the programme
from the student's current enrolment. This shortens the path from student to
completion status, which is the most frequent query in UC-03 and UC-09.

**Consequence accepted**
Completion queries now traverse `Student -> Enrolment -> CompletionCheck`
rather than reading from the student directly, making UC-03 and UC-09 slightly
more expensive to satisfy. We accept this because attaching the check to
`Student` makes the FR-08 eligibility status ambiguous as soon as a student has
two enrolments - the model could not say which programme a stored outcome
refers to.

**Traces to:** FR-04, FR-05, FR-06, FR-07, FR-08 - UC-03, UC-10

## Decision 3: `CompletionLetter` composes `VerificationCode`, but only associates to `LetterRequest`

**Context**
Composition is used in this model only where lifetime ownership genuinely
holds. Two relationships around the issued letter needed a defensible strength.
FR-13 requires each verification code to be permanently linked to its letter
record, while FR-14 requires an external party to be able to verify a letter
independently.

**Choice**
- `CompletionLetter "1" *-- "1" VerificationCode` - **composition**. The code
  exists solely to prove the authenticity of one letter, has no identity apart
  from it, and under FR-13 is permanently bound to it.
- `LetterRequest "1" -- "0..1" CompletionLetter` - plain **association**. The
  request causes the letter to be produced but does not own it. Once issued,
  the letter is an artefact external parties verify on their own initiative
  (`VerificationCode "1" -- "0..*" VerificationRequest`).

**Alternative considered**
Making `LetterRequest` compose `CompletionLetter` as well, so the whole
request-to-letter chain is owned end to end and the letter is destroyed with
the request.

**Consequence accepted**
Because the second relationship is a plain association, the model does not by
itself prevent a `LetterRequest` from being removed while its
`CompletionLetter` survives; referential integrity must be enforced by business
rule instead. We accept this because composition would mean deleting a request
destroys a letter an external verifier may still be checking, which directly
contradicts FR-14.

**Traces to:** FR-11, FR-13, FR-14 - UC-06, UC-07

## Decision 4: `ApprovalDecision` is separate from `LetterRequest`

**Context**
A request is something a student submits; an approval is something a
`RegistryOfficer` does. FR-09 lets staff review an assessment and FR-10 lets
them approve or reject it, with the outcome timestamped. FR-15 requires
approvals to appear in an audit trail alongside the actor who performed them.

**Choice**
`ApprovalDecision` is its own class, with `LetterRequest "1" -- "0..1"
ApprovalDecision` and `RegistryOfficer "1" -- "0..*" ApprovalDecision`. It
holds the decision, the date and the reason.

**Alternative considered**
Recording the outcome as `decision` and `decisionReason` attributes on
`LetterRequest`, with the deciding officer stored as a further attribute.

**Consequence accepted**
One more class and two more associations to keep consistent across artefacts.
We accept this because the attribute version gives the deciding officer no
modelled relationship - accountability would reduce to a name copied onto the
request, which is precisely what the FR-15 audit trail and the `AuditEntry`
class exist to avoid.

**Traces to:** FR-09, FR-10, FR-15 - UC-05, UC-11
