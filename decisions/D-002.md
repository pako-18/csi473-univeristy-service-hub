# D-002: Domain modelling decisions

**Project:** Student Completion Verification and Digital Letter Issuance System
**Laboratory:** 4 - Domain model, responsibilities and traceability
**Status:** Accepted
**Applies to:** `models/domain-model.*`, `docs/business-rules.md`, `docs/crc-cards.md`

---

## Decision 1: `LetterRequest` is a domain class, not a status attribute on `Student`

**Context**
UC-xx allows a student to request a completion letter. A student may request a
letter more than once - for example a first request that is rejected because the
completion record is incomplete, and a later request after the record is
corrected. Each request carries its own submission date, its own state
(submitted, under verification, issued, rejected) and its own outcome.

**Choice**
`LetterRequest` is modelled as its own class, associated to `Student` with a
multiplicity of `1 Student -- 0..* LetterRequest`. Request state, submission
timestamp and rejection reason are attributes of `LetterRequest`, not of
`Student`.

**Alternative considered**
Holding `letterStatus`, `requestDate` and `letterIssuedDate` as attributes
directly on `Student`. This is simpler and removes one class and one association
from the model.

**Consequence accepted**
The model carries an extra class, and any query for "this student's current
request" must navigate an association instead of reading a field. We accept this
because the attribute version can only hold one request at a time: a second
request would overwrite the first, destroying the history the registry needs
when a decision is queried later.

**Traces to:** FR-xx, FR-xx, UC-xx

## Decision 2: `Student` composes `CompletionRecord`, but `LetterRequest` only references it

**Context**
A completion record states whether a student has met all requirements of their
programme. A letter request must consult that record before a letter can be
issued. Both relationships needed a defensible strength, and composition should
only be used where lifetime ownership genuinely holds.

**Choice**
- `Student` **composes** `CompletionRecord` (`1 -- 0..1`). A completion record
  describes exactly one student and has no meaning or identity apart from that
  student; if the student is removed from the domain, the record goes with it.
- `LetterRequest` holds a plain **association** to `CompletionRecord`
  (`0..* -- 1`). The request consults the record; it does not own it.

**Alternative considered**
Making `LetterRequest` compose `CompletionRecord` as well, so that each request
carries the record it was decided against. This would make the evidence behind
each decision self-contained.

**Consequence accepted**
Because the association is plain, a completion record can be corrected after a
request has been decided, and the request will then point at data that differs
from what the decision was based on. We accept this and handle it with a rule in
`docs/business-rules.md` requiring an issued letter to store the record version
it was issued against, rather than duplicating the record itself. Duplicating
would have created two competing copies of a student's completion status, which
is worse than the versioning problem it solves.

**Traces to:** FR-xx, UC-xx

## Decision 3: `IssuedLetter` is separate from `LetterRequest`

**Context**
A request is a thing a student makes; a letter is a document the university
produces. Not every request produces a letter, and a letter, once produced,
becomes a verifiable artefact with a reference number that third parties may
check.

**Choice**
`IssuedLetter` is a separate class, associated `1 LetterRequest -- 0..1
IssuedLetter`. It holds the reference number, issue date, and the identity of
the issuing officer.

**Alternative considered**
Keeping one `LetterRequest` class with a status of `issued` and letter fields
that stay null until issue.

**Consequence accepted**
An extra class and an optional association to navigate. We accept this because
the single-class version leaves several attributes null for every rejected
request, and gives no clean place to attach verification of an existing letter -
a concern that belongs to the document, not to the request for it.

**Traces to:** FR-xx, UC-xx
